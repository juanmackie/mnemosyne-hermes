# Hermes Agent optimization research

**Research date:** 2026-10-08  
**Question:** What concrete changes would make the Mnemosyne provider work better in real Hermes sessions?  
**Audit baseline:** This repository requires no Hermes version. The findings below were audited against Hermes 0.18.2 and 0.19.0, from tags `v2026.7.7.2` and `v2026.7.20`. Hermes `main` was checked at commit [`a28a5d03a9fa60418db5f44f3436fa2aa029c8f2`](https://github.com/NousResearch/hermes-agent/commit/a28a5d03a9fa60418db5f44f3436fa2aa029c8f2), dated 2026-10-08 UTC. Findings about newer hooks are marked as future compatibility work, not as available in the audited releases.

## Findings

**Implementation follow-through:** The recommendations below record the
pre-change assessment. The implementation now includes source filtering,
accurate tool instructions, owned native-mirror correction, total context
budget/telemetry, opt-in exact-query cache, a public-prefetch eval, compact
setup, eligible-path backup discovery, Windows/PM installation, and
capability-gated newer lifecycle hooks. See the [configuration reference](HERMES_CONFIGURATION.md)
and [evaluation record](../bench/HERMES_PREFETCH_RESULTS.md). Newer main-source
checks are separate from the unchanged published-release support range; a live
gateway/model traffic experiment remains unexecuted.

The provider already follows several useful Hermes patterns. It exposes four tools by default and requires an explicit wildcard to expose the full engine surface, keeping tool schemas and risky operations out of the default prompt. Dynamic recall runs through `prefetch`, while `system_prompt_block` carries static instructions. This matches Hermes' separation between cached system-prompt state and per-call context. The provider also limits automatic writes to user turns by default, skips cron/flush/subagent/background/skill-loop contexts, makes delegation capture opt-in, and tracks session switches. The P22 consolidation worker separates model inference from foreground DB access. These are meaningful product behaviors to preserve while optimizing. See [the provider implementation](../integrations/hermes-provider/hermes_memory_provider/__init__.py), [the canonical Hermes integration guide](HERMES_INTEGRATION.md), and Hermes' [prompt assembly guide](https://hermes-agent.nousresearch.com/docs/developer-guide/prompt-assembly).

The static prompt instructions have two mismatches with the actual Hermes setup. The block tells the model to use `mnemosyne_shared_*` tools, although those tools are absent from the four-tool default schema. It also calls Hermes' built-in memory tool deprecated, while Hermes keeps its `MEMORY.md` and `USER.md` stores active alongside an external provider. Clarify the roles: keep Hermes' small native memory for session-independent user/profile anchors, use Mnemosyne for searchable episodic evidence and richer facts, and use skills for procedural instructions. Mention only Mnemosyne tools that `get_tool_schemas()` actually exposes, or phrase advanced shared tools as conditional on explicit configuration. Retain `session_search` as an available history fallback when prefetch is insufficient. This is a high-confidence prompt-quality fix grounded in the provider's configured tool set and Hermes' [persistent memory contract](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/).

Automatic recall is a direct latency target, but this research did not benchmark the complete provider path. Hermes 0.18.2 calls `prefetch` directly; 0.19.0 waits for it through a timeout-bounded worker. Mnemosyne's `prefetch` performs bank recall and also reads identity/model-slot context; the `queue_prefetch` hook is currently a no-op. Both supported releases have the hook and send it the just-completed user query on the post-turn path. That offers an exact-query prewarm opportunity, but the query can change on the next turn, so the expected hit rate must be measured before treating this as a latency win. Provider-side work and returned context still need their own practical size/latency bounds. See the [0.18.2 provider contract](https://github.com/NousResearch/hermes-agent/blob/v2026.7.7.2/agent/memory_provider.py), [0.18.2 manager](https://github.com/NousResearch/hermes-agent/blob/v2026.7.7.2/agent/memory_manager.py), [0.19.0 manager](https://github.com/NousResearch/hermes-agent/blob/v2026.7.20/agent/memory_manager.py), and [local prefetch path](../integrations/hermes-provider/hermes_memory_provider/__init__.py).

Automatic context quality needs a targeted audit. The provider classifies raw transcript rows using source `conversation` and content prefixes such as `[USER]` and `[IDENTITY]`. Opt-in tool and delegation capture use `conversation_tool` and `conversation_delegation`; those source names do not currently receive the raw-transcript penalty. As a result, captured operational text may enter silent prefetch as if it were a distilled fact. This is a correctness and prompt-cost risk, especially for tool output and child-agent summaries. Label those sources as raw, keep their injection opt-in or disabled by default, and add relevance cases before changing ranking. See the filtering helpers and branches in [the provider](../integrations/hermes-provider/hermes_memory_provider/__init__.py).

Native memory corrections can also leave stale mirrors. `on_memory_write` handles `add` and `replace` by remembering content, without explicitly retiring the prior mirror, and ignores `remove`. A corrected or deleted native fact can therefore survive in Mnemosyne's searchable state. Current Hermes supplies authoritative `metadata["previous_content"]` for replace/remove, but older callers can omit it. Introduce an explicit native-entry-to-engine-ID mapping where a reliable identity exists, retire only that mirror, and test add → replace → remove across supported releases. Do not infer entry identity from a broad text search or erase unrelated memories when older metadata is insufficient. See the [local mirror callback](../integrations/hermes-provider/hermes_memory_provider/__init__.py) and [current native-write contract](https://github.com/NousResearch/hermes-agent/blob/a28a5d03a9fa60418db5f44f3436fa2aa029c8f2/agent/memory_provider.py#L166).

Prompt size is bounded per item in some configurations, but the aggregate prefetch block has no universal token/character ceiling. Identity and model-slot blocks are composed in addition to the ranked bank results. Hermes' current docs describe spill handling for oversized results, but that behavior is newer than the supported 0.18.2/0.19.0 contract. A provider-level total-output cap therefore remains useful for the supported range. Preserve deterministic identity visibility while budgeting the complete returned string, and expose counts/truncation in diagnostics rather than silently cutting facts. See the [current provider plugin guide](https://hermes-agent.nousresearch.com/docs/developer-guide/memory-provider-plugin/) and [local formatting path](../integrations/hermes-provider/hermes_memory_provider/__init__.py).

Capture and compression hooks are present in the local provider, but they have distinct roles. `sync_turn` records configured roles after each completed turn; the default is user-only. `on_delegation` records bounded parent-side task/result text only when the operator enables the delegation role. `on_pre_compress` contributes bounded user/assistant excerpts and can write a local snapshot, but Hermes 0.18.2 and 0.19.0 catch hook exceptions and continue compression. Thus `require_checkpoint` is a local write requirement, not a fail-closed guarantee against transcript loss. Current Hermes `main` adds an opt-in API-v2 checkpoint contract and an operator gate; this provider does not advertise that version and the feature must not be enabled as if it were supported today. See the [supported provider source](https://github.com/NousResearch/hermes-agent/blob/v2026.7.7.2/agent/memory_provider.py), [supported manager implementation](https://github.com/NousResearch/hermes-agent/blob/v2026.7.7.2/agent/memory_manager.py), [current provider contract](https://github.com/NousResearch/hermes-agent/blob/a28a5d03a9fa60418db5f44f3436fa2aa029c8f2/agent/memory_provider.py), and [current compression documentation](https://github.com/NousResearch/hermes-agent/blob/a28a5d03a9fa60418db5f44f3436fa2aa029c8f2/website/docs/developer-guide/memory-provider-plugin.md).

One conditional maintenance opportunity is database backup discovery. Hermes 0.18.2/0.19.0 define `MemoryProvider.backup_paths()` for provider state outside `HERMES_HOME` but inside the operating-system user's home; the local class does not override it. Hermes skips paths outside the user's home even if the provider declares them. A hook could improve coverage only for eligible paths, and must resolve configuration on a fresh, uninitialized provider without opening the live DB. It cannot solve backups of arbitrary external paths. Verify SQLite/WAL snapshot consistency and restore behavior before changing the documented limitation in `CONTRACT_AUDIT.md` F4. See [0.19.0 backup implementation](https://github.com/NousResearch/hermes-agent/blob/v2026.7.20/hermes_cli/backup.py), [0.18.2 MemoryProvider](https://github.com/NousResearch/hermes-agent/blob/v2026.7.7.2/agent/memory_provider.py), and [the local audit](../integrations/hermes-provider/CONTRACT_AUDIT.md).

Native Windows is a product gap in installation ergonomics. Hermes lists native Windows as a supported platform and provides a PowerShell installer; this repository ships `install.sh`, while its provider documentation describes `--copy` as the route when directory symlinks are unavailable. A PowerShell companion could resolve the active Hermes home and Python environment, install the same pinned engine/provider, apply the same engine patch, produce the same verified copy provenance, and configure/verify the provider. This should be based on Hermes' Windows install ownership and path rules, then tested against supported Hermes installs; do not infer paths from Unix conventions. See [Hermes native Windows guide](https://hermes-agent.nousresearch.com/docs/user-guide/windows-native), [Hermes platform support](https://hermes-agent.nousresearch.com/docs/getting-started/platform-support), and [the repository installer](../install.sh).

Hermes' current provider docs also recommend keeping setup schemas small because every schema field may become a setup prompt. Mnemosyne currently places many advanced tuning and lifecycle options in `get_config_schema()`. If the supported versions' setup flow prompts for every field, reduce the wizard to essential choices and leave advanced controls in the documented config reference; validate this with the release tags before editing. This is a lower-confidence UX recommendation because setup presentation may differ by release. See [Hermes' provider setup guidance](https://hermes-agent.nousresearch.com/docs/developer-guide/memory-provider-plugin/#config-schema) and [the local schema](../integrations/hermes-provider/hermes_memory_provider/__init__.py).

Group-chat attribution is another future upgrade opportunity. Current Hermes `main` passes `turn_author` to `sync_turn` when the provider accepts it and supplies per-turn author fields to `on_turn_start`; the local method currently tracks only the turn number, and `sync_turn` accepts no `turn_author`. This could let the provider attach the actual speaker to captured evidence in shared gateway sessions. It is outside the current audited contract: add it only after adopting and testing a Hermes release that provides these fields, and do not use a process-level initial `user_id` as a substitute for the current speaker. Keep author provenance separate from visibility/isolation rules. See the [current manager source](https://github.com/NousResearch/hermes-agent/blob/a28a5d03a9fa60418db5f44f3436fa2aa029c8f2/agent/memory_manager.py) and [current provider source](https://github.com/NousResearch/hermes-agent/blob/a28a5d03a9fa60418db5f44f3436fa2aa029c8f2/agent/memory_provider.py).

## Baseline and evaluation plan

There is a standalone lite recall benchmark, but it does not measure the engine-backed Hermes provider's automatic prompt path. Add a separate provider evaluation lane before ranking changes:

1. Seed an isolated pinned-engine database with labelled preferences, identity facts, canonical profile facts, distilled insights, raw user/assistant turns, tool captures, delegation captures, duplicates, stale/superseded rows, and unrelated high-importance rows. Include multi-session and multi-profile cases.
2. Use a fixed query set covering greetings, short follow-ups, direct fact questions, paraphrases, tool-heavy coding turns, delegation summaries, no-match queries, and unrelated topic switches. Record expected relevant IDs and any identity rows that must always appear.
3. Measure cold and warm `prefetch` p50/p95, lock wait, SQL/recall time, output characters and estimated tokens, number of returned rows by source, and exact-query prewarm hit rate. Keep timeouts and failed recall separate from legitimate no-match results.
4. Grade precision@5/recall@5 or MRR for ranked memories, identity coverage, irrelevant-injection rate, duplicate rate, truncation rate, and whether the injected block contains sensitive tool output. Compare current behavior against each change on the same corpus and queries.
   Replay native add/replace/remove and user corrections to verify that superseded mirrors stop surfacing. Persist only intentional durable facts globally; changing `default_scope` to global also changes raw autosave scope and is not a general optimization.
5. Run representative turns through each supported Hermes release, including a tool loop, `/new` or session switch, compression, a delegated task, a gateway thread, and backup/restore. Capture actual model-input token counts where the client exposes them; Hermes' offline `hermes prompt-size` is useful for fixed prompt/tool-schema cost but does not by itself measure dynamic prefetch content.

Do not tune for lower latency alone. A change is an improvement only if it reduces p95 prefetch latency or injected tokens without lowering recall/identity coverage or increasing irrelevant and sensitive context. The [Hermes tips](https://hermes-agent.nousresearch.com/docs/guides/tips) identify tool schemas, memory, skills, and system prompt as fixed prompt cost and recommend `hermes prompt-size`; the [prompt assembly guide](https://hermes-agent.nousresearch.com/docs/developer-guide/prompt-assembly) explains why dynamic recall belongs in the API-call-time path while static provider instructions belong in the cached prompt.
