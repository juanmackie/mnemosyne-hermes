# memoryrepo upstream review

Reviewed `supermemoryai/memoryrepo` at [`54f7ff3065df8af687dc5c04a4bb17d6611e5fd1`](https://github.com/supermemoryai/memoryrepo/commit/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1), against this repository's contracts in [AGENTS.md](../AGENTS.md) and its two-surface architecture in [README.md](../README.md). This is a proposal only; no implementation is included.

## Recommendation

Borrow the upstream's explicit source references and stale-write conflict discipline as design patterns. Treat dream-style cleanup as a later, opt-in engine-backed workflow with auditable previews. Keep Mnemosyne's SQLite/engine data model, local keyless behavior, conservative indexing, existing installer and provider provenance gates, and current test strategy. Do not transplant the upstream server, cloud storage, git vault, FTS indexes, or direct paid-model integration.

## Transferable patterns, in priority order

### 1. Make provenance actionable (high value, modest scope)

Memoryrepo asks for one fact per bullet with a source and date, and defines stable source formats for a transcript message or note ([memory conventions](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts#L41-L46), [chat write instructions](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts#L51-L59)). Its dreamer can reopen a source and receive a bounded excerpt ([source lookup](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L292-L304), [excerpt window](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/transcripts.ts#L83-L100)). But if the cited message ID is missing, `sourceExcerpt` labels the problem and returns the last 12 messages; the excerpt is capped at 8,000 characters. Thus the tool does not always verify the cited statement. Citations are requested in prompts, not enforced by the write API.

**Proposal:** preserve this behavior when using the Hermes engine's existing validation/provenance tools. For Lite, first improve display, read-by-ID, or export of the existing `context` field; it has no dedicated source field ([lite schema and write API](../src/mnemosyne_lite/storage.py#L110-L123), [remember API](../src/mnemosyne_lite/storage.py#L1024-L1068)). That offers a no-schema path to inspect available context. If a future source-link feature is proposed, keep it optional for direct CLI/MCP writes and require exact source availability: a missing reference must be reported unavailable, never substituted with unrelated recent messages. Do not claim a prompt-produced citation is verified or import Memoryrepo's Markdown bullet format into the engine provider.

### 2. Preserve conservative conflict handling (high value, already aligned)

Chat writes carry the version the agent read. If another writer has changed a touched file, `applyEdits` rejects the write and returns the current contents for reconciliation; non-overlapping changes may proceed ([write conflict check](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L316-L346), [agent retry instructions](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts#L53-L59)). A dream computes a three-way merge and refuses the whole result if both sides changed the same path ([dream rebase and conflict branch](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L402-L425)).

**Proposal:** use this as a review criterion for provider-facing concurrent mutation or any future batch consolidation: identify the read version, detect overlap, surface the conflicting current record, and leave ambiguous edits unapplied. This repository already has strict ownership markers for native mirrors and engine claim semantics ([provider behavior](../integrations/hermes-provider/README.md#background-consolidation)); preserve those and do not add another registration path. The upstream relies on a single Durable Object serializing pushes, so its implementation is not a drop-in concurrency primitive for SQLite or multiple local processes.

### 3. Keep maintenance incremental and inspectable (medium value, larger scope)

The upstream supplies messages and notes newer than persisted cursors to its periodic dream, then advances cursors after a successful Git push ([inbox construction](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/transcripts.ts#L60-L80), [maintenance commit and cursor advance](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L402-L429), [cursor persistence](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L440-L465)). These are separate Git and SQLite writes, so commit and cursor advancement are not atomic; the design alone does not establish lossless processing or reversibility. The dream has an explicit step ceiling, a stop callback, a read-only inbox, a bounded source-reading tool, and one final commit tool ([dream loop and tool boundary](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts#L68-L92), [loop implementation](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts#L176-L242)).

**Proposal:** if extending existing Hermes consolidation, favor bounded batches and a dry-run or reviewable change set. Specify how writes and checkpoints behave across partial failures; do not assume that separate data stores advance atomically. Use engine lifecycle tools, Hermes' active model proxy, and existing `dry_run` coverage; do not create a parallel LLM maintenance system for lite. The repo already has an exact-duplicate-only apply rule and reports prefix collisions as proposals, specifically because similar prefixes can encode different facts ([lite consolidation policy](../src/mnemosyne_lite/storage.py#L1304-L1324)). Keep that safety bar: upstream's LLM-directed merge/delete behavior is a model policy, not a correctness guarantee.

### 4. Measure indexes against write and recall cost (medium value, already practiced)

Memoryrepo lazily synchronizes FTS indexes, indexing only new transcript messages and rebuilding the wiki index only when the commit hash changes ([index schema](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L55-L74), [lazy index sync](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L514-L576)). This is appropriate for its separate search corpus and storage architecture. Mnemosyne Lite already uses external-content FTS5 with content-change triggers and only two retained secondary indexes; its own comments record a measured index removal that made writes slower despite fewer dirty pages ([lite FTS and index rationale](../src/mnemosyne_lite/storage.py#L125-L180)).

**Proposal:** adopt the upstream's lazy/index-versioning approach only for a future derived corpus that cannot be maintained transactionally with the source rows. For current schema changes, keep benchmarking the actual write, checkpoint, and recall paths and retain indexes based on measured end-to-end behavior. Do not copy its three FTS tables: the lite store's corpus is smaller and already has a single authoritative memory table and FTS index.

### 5. Treat cost accounting as optional observability, not a dependency (low direct fit)

Upstream wraps every model invocation, records input/cache/output tokens, provider-reported spend and latency ([meter wrapper](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/models.ts#L36-L74)), then enforces an account-wide monthly spend cap by stopping chat/dream steps ([budget and stop logic](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/chat-agent.ts#L68-L90), [dream budget](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L364-L396)). That system depends on OpenRouter pricing and a paid API key ([model setup](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/models.ts#L26-L34)).

**Proposal:** retain per-operation latency, token, and action counts where Hermes exposes them, especially for prefetch and consolidation evaluation. Do not add OpenRouter, a second model key, USD pricing tables, or a mandatory monthly cap: this repository is keyless by design and optional LLM operations inherit Hermes' model/proxy. Cost data must never gate core memory reads/writes.

### 6. Add tests for observable contracts, not the upstream architecture (high confidence)

The pinned upstream tree contains no test/spec files; its README describes behavior, but the contracts above do not have a visible upstream test suite in this snapshot. Mnemosyne already has regression coverage around schema refusal/migration, duplicate handling, recall freshness, and provider-engine behavior ([test registry](../AGENTS.md#verification), [lite hardening tests](../tests/test_python_hardening.py)).

**Proposal:** any adopted behavior should add a focused regression case to the existing suite: source-reference round-trip and missing-source behavior; concurrent same-record conflict preserving both versions; failed maintenance not advancing its cursor; and bounded maintenance not committing when interrupted. Register any new gate in `scripts/checks.sh`. Avoid reproducing the upstream's untested chat UI, git operations, or cloud agent lifecycle as tests for this local Python project.

## Patterns to reject or defer

- **Git/Markdown as the canonical store:** the upstream's entire model is a per-user Git repository with a commit per write ([architecture summary](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/README.md#L20-L42)). Mnemosyne's provider is engine-backed and Lite is an intentionally small SQLite keyword store. Replacing either would break the product contract.
- **Cloudflare and web application stack:** memoryrepo's storage, scheduler, identity, UI and API are built around Cloudflare Durable Objects, Artifacts, alarms, and an OpenRouter-backed web service ([runtime stack](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/README.md#L35-L45), [server dependencies](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/package.json)). These introduce network, account, secret, and runtime requirements absent from Mnemosyne.
- **A background LLM janitor for Lite:** dreamer can rewrite or remove facts from model judgment. Keep Lite deterministic and keyless. Any richer consolidation belongs to the existing engine-backed optional path and must preserve source evidence and preview/rollback semantics.
- **Unmeasured extra indexes or duplicate corpora:** the upstream indexes conversations, wiki files, and notes because its web app searches all three. That workload is not evidence that another index helps our provider or Lite store.

## Proposed sequence

1. Audit current provider provenance/validation and Hermes prefetch diagnostics against the source-linking pattern; document any concrete gap before changing code.
2. If a caller needs source evidence on Lite, design a separate backward-compatible API/schema proposal and migration before implementation; keep it optional and local.
3. For any maintenance enhancement, specify conflict, interruption, checkpoint, preview, and rollback behavior first, then add focused contract tests and register the gate.
4. Continue measurement-led index and cost/latency work through existing benchmarks and diagnostics; do not import the upstream's paid service infrastructure.
