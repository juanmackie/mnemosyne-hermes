# Memoryrepo patterns for the Hermes provider

**Reviewed:** 2026-10-09 (Australia/Brisbane)  
**Local revision:** `5a1eb57cd844a2c58c5a5c5c330df04fffaca306`  
**Upstream revision:** [`supermemoryai/memoryrepo` `54f7ff3065df8af687dc5c04a4bb17d6611e5fd1`](https://github.com/supermemoryai/memoryrepo/tree/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1)

This is a provider-focused proposal. It does not recommend replacing Mnemosyne's engine, adding a second memory backend, or changing the lite product. Memoryrepo is a hosted Git-backed memory application; the useful comparison is its user-facing inspection and provenance workflow, not its storage architecture.

## What the comparison shows

Memoryrepo makes it easy to inspect a fact, follow its source, compare revisions, and see when automated maintenance ran. Its conventions ask for one fact per line with a source reference; chat and dream instructions tell the agent to read cited conversations when checking contradictions. The README describes a file tree, backlinks, graph, commit diffs, dream log, and per-turn/dream costs ([README](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/README.md#L4-L13), [memory instructions](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts#L41-L92)). These source references are model-written conventions; they are not proof that a citation exists or supports the statement.

The provider already has several comparable foundations: engine-backed search and export, a bounded automatic-context path and diagnostics, optional session/tool capture, explicit remember source and metadata fields, author metadata when Hermes supplies it, canonical-slot history, and asynchronous consolidation using an independent connection ([provider `__init__.py`](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L3083), [configuration](HERMES_CONFIGURATION.md#L34), [canonical history](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L4038), [consolidation audit](../integrations/hermes-provider/CONTRACT_AUDIT.md#L393)). These are real capabilities, but they do not currently add up to a general, user-facing memory history or source-verification workflow.

The concrete gap to address first is inspectability. The provider has an internal SQLite audit table, but the connection is created on initialization's thread and retained in `AuditLog`; standard `sqlite3.connect` enforces same-thread use. Provider event writes can happen on other threads, and both `record()` and the read methods swallow failures. A worker-thread write therefore disappears while appearing successful; a failed query/count looks like empty history ([`audit.py`](../integrations/hermes-provider/hermes_memory_provider/audit.py#L47), [provider audit wrapper](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L1674)). The provider CLI offers search, stats, sleep, export and import, but no by-ID history command; its export invokes the engine's whole-store JSON export using `hermes_default` as the session ([CLI registration](../integrations/hermes-provider/hermes_memory_provider/cli.py#L335), [CLI export](../integrations/hermes-provider/hermes_memory_provider/cli.py#L563)). The engine export includes all sessions and `summary_of` fields, while ordinary `get` omits `summary_of`; do not present that export as a visibility-filtered inspection view ([pinned engine `beam.py`](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L4310), [export implementation](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L8876)).

Audit coverage is also partial. Explicit remember logs an event without its supplied source or metadata; successful `_handle_update` does not emit one. Some other provider operations do emit events, but the existing table must not be advertised as complete or undoable ([remember and audit call](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L3512), [update handler](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L4335)). `tokens_used` is a nullable audit column but the calls inspected do not populate it. Consolidation is tracked in memory as one running thread, is best-effort, and has no persistent job record; reflection-budget reservation exists, but it is not a user-visible cost ledger ([audit schema](../integrations/hermes-provider/hermes_memory_provider/audit.py#L20), [worker lifecycle](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L3249), [budget reservation](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L2023)).

One lineage detail needs a baseline before any provenance feature is promised. In pinned engine 3.15.1, direct `consolidate_to_episodic` writes `summary_of` to the episodic row, while automatic sleep passes metadata such as `original_count`, `source`, and `llm_used`; `get` selects `metadata_json` but not `summary_of`, whereas export includes `summary_of` ([pinned engine consolidation](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L4476), [automatic sleep](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L8549), [`get`](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L4310), [export](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L8876)). This means source-reference survival through automatic sleep is not established by the working-memory metadata path. The implementation plan starts with a round-trip audit and treats missing lineage as a result, not an assumption.

## Recommended slices

### 0. Establish lineage across engine lifecycle operations

**Owner:** provider contract tests plus the pinned-engine contract lane; engine behavior changes belong upstream or through the already-audited engine patch process.

Before attaching citations or generating a readable export, capture what survives `remember → get → update/validate → automatic sleep → get/export`. Include identifiers, source, metadata, `summary_of`, scope/session visibility, and history retention. In pinned engine 3.15.1, direct `consolidate_to_episodic` writes `summary_of` to the episodic row, while automatic sleep passes metadata such as `original_count`, `source`, and `llm_used`; `get` selects `metadata_json` but not `summary_of`, whereas export includes `summary_of` ([pinned engine consolidation](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L4476), [automatic sleep](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L8549), [`get`](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L4310), [export](https://github.com/mnemosyne-oss/mnemosyne/blob/v3.15.1/mnemosyne/core/beam.py#L8876)). This means source-reference survival through automatic sleep is not established by the working-memory metadata path. Determine whether source information is recoverable through `summary_of`, engine metadata, audit events, or only export. Do not infer that an exact source reference survives consolidation just because it was stored on a working row.

**Acceptance:** engine-backed fixtures document each operation's actual field-level result against the pinned engine; references lost from normal reads or sleep are explicitly marked unsupported until the provider or engine supplies a safe path. No schema changes in this characterization slice.

### 1. Repair and characterize audit inspection

**Owner:** this repository's provider integration. Keep the engine as the source of memory rows and preserve the provider's existing SQLite and locking design.

First make audit persistence safe for the real calling threads, with explicit tests for initialization-thread and worker-thread events. Use one connection per thread (or another strategy proven compatible with the provider's locks and lifecycle); simply disabling SQLite's thread check is not enough. Surface a bounded failure counter/status in diagnostics. Preserve best-effort mutation semantics while bounding audit write overhead: the current SQLite connection uses a five-second busy timeout, so an outage or lock can currently delay a caller before the error is swallowed. Choose and test an appropriate short bound or a non-blocking handoff without adding an unbounded queue. Make a failed history read report an error rather than return an empty list. Avoid logging arbitrary memory text or unbounded metadata.

Then add a read-only, bounded `hermes mnemosyne history` or `inspect --id` command that can show event time, action, memory ID, source tool, scope/profile/session where access permits, and a sanitized allowlist of metadata. Make partial coverage explicit. Cover update and other supported mutations before describing the result as a timeline. Define how history for a forgotten/deleted row remains access-controlled; filtering by joining only to currently live memory rows would hide deletion events and cannot itself establish authorization. Do not add another Hermes provider tool or alter the four default tools ([canonical tool table](HERMES_INTEGRATION.md#canonical-tool-names-and-default-exposure)).

**Acceptance:** a regression test demonstrates the worker-thread write was lost before the fix and is readable after; injected SQLite failures stay visible in diagnostics and fail history reads; bounded output and metadata allowlisting are tested; visibility tests cover another session/profile and deleted IDs. Remove the `_init_audit_log` stub from the strict engine fixture for this lane, or add a focused provider test that exercises the real implementation. Register any new gate in [`scripts/checks.sh`](../scripts/checks.sh). Preserve partial-history wording until event coverage is actually complete.

### 2. Attach exact source references where Hermes provides them

**Owner:** provider normalization and provider tests first; any missing stable message-ID hook belongs in the Hermes host integration. Engine schema changes belong upstream unless the existing metadata path is demonstrated insufficient.

The provider currently accepts the full `messages` list for opted-in tool capture, but the stored tool metadata contains role/name/turn author, not a stable message reference. User and assistant capture stores turn author metadata, also without a message reference ([`sync_turn`](../integrations/hermes-provider/hermes_memory_provider/__init__.py#L3083)). Preserve an exact message or thread reference only when the host supplies a stable ID. Keep that reference distinct from author identity and session/profile visibility. A transcript search can help locate evidence, but it cannot prove that a specific source supported a memory.

**Acceptance:** round-trip supported exact references through remember/get and every supported consolidation/update path; older hosts show source unavailable rather than a guessed ID; visibility checks apply to source lookup; an unknown or deleted source is an explicit unavailable result. Do not create a new engine field or migration until these tests establish the current metadata cannot retain the reference.

### 3. Add a read-only Markdown projection after visibility rules are proven

**Owner:** provider CLI/export layer, using engine-visible rows. Do not add a second backing store or Git write path.

Memoryrepo's linked Markdown makes memories easy to browse and diff. A Mnemosyne export can borrow that readability without borrowing Git as the database: render a read-only projection with stable memory IDs and any verified source references, while retaining the existing JSON export. Before doing so, define visibility using the engine's supported read helpers. The current whole-store export is not evidence that its output is safe for a per-session inspection view.

**Acceptance:** compare projected IDs and source references to the eligible source rows; test session/profile boundaries; mark missing provenance; preserve JSON export compatibility; prove export is read-only. Keep an index bounded in code and put details in on-demand topic files only if users demonstrate that need.

### 4. Add maintenance progress before cost reporting

**Owner:** provider lifecycle/diagnostics for status; engine or Hermes proxy instrumentation for reliable token/cost data.

Memoryrepo exposes a dream log and a cost ledger ([README](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/README.md#L10-L35)). Mnemosyne already tracks a single consolidation worker and a reserved reflection budget, but that state is volatile and diagnostics do not give an operator a durable run record. A small status surface could expose trigger, start time, running/completed/failed/deferred state, and sanitized failure class. Only report token or money cost if Hermes' active proxy or the engine supplies measured usage; do not estimate it from character counts or add a second model key. The existing no-key and active-Hermes-model contracts still apply ([`AGENTS.md`](../AGENTS.md#L80)).

**Acceptance:** deterministic lifecycle tests cover start, duplicate trigger, completion, error, timeout/shutdown, and reinitialization; status contains no prompt or memory text. Cost fields remain absent when usage is unavailable and match upstream-reported usage when available. Avoid a persistent job queue until actual crash-recovery requirements justify one.

## Do not prioritize

- **A parallel transcript index or context wiki.** Memoryrepo's grep-and-follow-links loop fits its Markdown vault ([README](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/README.md#L4-L10)). This provider already uses Mnemosyne hybrid retrieval, filters and budgets automatic context, and documents Hermes `session_search` as the transcript fallback ([configuration](HERMES_CONFIGURATION.md#L34), [integration guide](HERMES_INTEGRATION.md#L101)). No retrieval or latency gap is established here; use the existing prefetch evaluation before proposing another index.
- **Git-backed memory storage, hosted notes UI, Durable Object scheduling, or OpenRouter selection.** Those duplicate engine or host responsibilities and change the product boundary. Memoryrepo also has application-specific optimistic Git conflict checks ([`memory-agent.ts`](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts#L317-L347)); Mnemosyne has its own SQLite transactions, visibility rules and recently audited consolidation concurrency ([`CONTRACT_AUDIT.md`](../integrations/hermes-provider/CONTRACT_AUDIT.md#L393)).
- **Prompt-only provenance claims.** Memoryrepo's source format and source-reading instructions are useful conventions ([`memory.ts`](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts#L41-L92)); they do not make citations verified. An exact host message reference plus a permission-checked lookup is the useful provider adaptation.
- **Immediate changes to the lite surface.** It is a separate keyword-store product, not the Hermes provider. The provider gaps above should be resolved on the provider side before proposing lite card or export additions.

## Implementation constraints

Any edit under the vendored provider must follow the snapshot process: a `# LOCAL PATCH:` marker, a `PATCHES.md` entry, and updated hashes/bytes/lines in `VENDORED_FROM.json`, then `python tests/test_vendored_provider.py`. Preserve the pinned engine range, single provider registration, four default tools, DB precedence, keyless operation and Hermes model inheritance. A change to engine lineage or engine schema belongs upstream or requires the repository's audited engine-patch process. The current engine-backed contract lane covers tool behavior, ID visibility and write/read coherence, but its fixture currently stubs audit initialization; extend it only where it gives meaningful audit coverage ([engine contract fixture](../tests/test_provider_engine_contract.py#L147)).

The pre-existing [`MEMORYREPO_RESEARCH.md`](MEMORYREPO_RESEARCH.md) is preserved. This provider review independently checked the cited local code paths and the pinned upstream repository; no implementation or other documentation changes are part of this proposal.
